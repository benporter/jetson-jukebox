# Request dashboard

A small always-on web UI for reviewing what kids asked for, what played, what
**failed**, and what got **blocked** — plus a disk-health gauge. It's the read
side of the DuckDB request log (`docs/data-logging.md`); it never writes.

- **URL:** `http://jetson-orin-nano.local:8088/` (shown, clickable, in the SSH
  login banner). The mDNS `.local` name is used instead of the IP so the link
  survives DHCP address changes (resolves via avahi on the LAN). Port/bind in
  `config/jukebox.env`.
- **Service:** `jukebox-dashboard.service` (part of `jukebox.target`, starts on
  boot, `Restart=always`).
- **Stack:** FastAPI + uvicorn (one worker), DuckDB-over-Parquet, vendored
  Grid.js. No pandas. ~70 MB resident.

## Why it can't lock the database (the key design point)

DuckDB is **single-writer**. The pipeline (`jukebox-pawkey`) opens the live DB
read-write, briefly, once per request. If the dashboard held its own connection
to that file it could collide with those writes.

So the dashboard **never reads the live file on a page view.** Instead
`src/dashboard/snapshot.py` touches the live DB **read-only, once every
`JUKEBOX_DASH_SNAPSHOT_SECONDS` (default 60 s)** and exports the `requests` table
to a Parquet snapshot (`data/dashboard/requests.parquet`, written atomically via
a temp file + `os.replace`). Every API query reads that snapshot
(`src/dashboard/queries.py`), so:

- Page views, filters, sorts → **zero** contact with the live DB.
- Live-DB contact is one short read per minute, fully decoupled from HTTP load;
  the writer already retries on a lock (`src/db.py::_connect`), so the rare
  overlap is absorbed and playback is never blocked.
- Tradeoff: the view is up to ~60 s stale. The page header shows snapshot age
  (and flags it amber if > 180 s).

## What it shows

- **KPI strip** (for the selected range): Requests · Played (% of total) ·
  Failed · Blocked. Counts come from `/api/stats` (server-side, **not** capped by
  the table's row limit), so they're correct at any volume.
- **Disk card:** root free %, with a bar that turns amber under
  `JUKEBOX_DISK_WARN_PCT` (default 10%) and red under half that; plus DB / WAL /
  snapshot sizes and snapshot age. (Today the box is ~93% free — this is an
  early-warning gauge, not a current concern.)
- **Tuning cards:**
  - *Top titles that failed to play* — `no_match` / `play_failed` grouped by
    `intent_title`. This is where artist-hallucination shows up (e.g. "It's Your
    Birthday" failing repeatedly) and feeds the transcript-grounding work.
  - *Most-blocked artists* — `outcome LIKE 'blocked%'` grouped by artist; live now
    that the explicit gate blocks (and grows with the per-artist blocklist).
- **Interactive table** (Grid.js): sortable + client-side search over the
  time/status/room-filtered set. Columns: time, heard (transcript), title,
  artist, the track/artist Spotify returned, **explicit** badge, outcome badge,
  room, volume, block reason, error.
- **Filters:** status chips (All / Played / Failed / Blocked), a time range
  (24h / 7d / 30d / Today / All), and a room dropdown. The view auto-refreshes
  every 30 s.

## API

All read-only, all over the snapshot:

| Route | Returns |
|---|---|
| `GET /api/requests?status&room&q&from&to&limit` | filtered rows, newest first |
| `GET /api/stats?status&room&q&from&to` | counts + tuning lists |
| `GET /api/disk` | disk usage + file sizes + warn level |
| `GET /api/rooms` | distinct rooms seen (for the dropdown) |
| `GET /healthz` | liveness (used by `jukebox_healthcheck.sh`) |

`status` is one of `all` / `played` / `failed` (`no_match`+`play_failed`) /
`blocked` (`outcome LIKE 'blocked%'`). `from`/`to` are local-time ISO timestamps
compared against `requested_at`.

## Config (`config/jukebox.env`)

```
JUKEBOX_DASH_PORT=8088
JUKEBOX_DASH_BIND="0.0.0.0"        # LAN-reachable; 127.0.0.1 restricts to the box
JUKEBOX_DASH_SNAPSHOT_SECONDS=60
JUKEBOX_DISK_WARN_PCT=10
```

There is **no authentication** — it's intended for a trusted home LAN. To lock it
to the box only, set `JUKEBOX_DASH_BIND=127.0.0.1` and tunnel over SSH.

## Operate

- Install/refresh (after editing the unit): `setup/install_services.sh` (sudo).
- Restart after a code/config change: `sudo systemctl restart jukebox-dashboard`.
- Logs: `journalctl -u jukebox-dashboard -f`.
- Health: `setup/jukebox_healthcheck.sh --status` lists `dashboard`.
- The snapshot can be regenerated by hand: `python3 -m src.dashboard.snapshot`.

## Data retention & export

- **Retention is PERMANENT — the request history is never purged.** The `requests`
  table is append-only by intent (it's a dataset that builds up over time). There
  is no retention window, `DELETE`, `DROP`, or cleanup job anywhere — and there
  must not be one (see the banner in `src/db.py`). The data is tiny: ~a few hundred
  bytes/row, so the full history is single-digit MB even over years.
- **The table's row `limit` is a DISPLAY cap, not a data cap.** `/api/requests`
  renders up to `limit` rows (default **1000**, max **100000**); the KPI counters
  are computed uncapped, so totals are always accurate. Older rows still exist —
  filter by date to reach them, or export the whole thing (below).
- **Export the full history** with `setup/export_requests.py` (reads the DB
  **read-only**, safe while the jukebox is playing):
  ```
  python3 setup/export_requests.py                    # CSV  -> data/exports/requests-<n>.csv
  python3 setup/export_requests.py -f parquet         # Parquet (typed, compact — best for analysis)
  python3 setup/export_requests.py -f jsonl           # one JSON object per line
  python3 setup/export_requests.py -f json            # one JSON array
  python3 setup/export_requests.py -o ~/toy/data.csv  # choose the path
  python3 setup/export_requests.py -f jsonl --out -   # stream to stdout (pipe it)
  ```
  `data/exports/` is gitignored (under `data/`). To pull it to another machine:
  `scp jetson@<box-ip>:/home/jetson/development/data/exports/requests-*.parquet .`
  (or `scp` the raw `data/jukebox.duckdb` and open it read-only with DuckDB).
- **Column meanings** for the exported schema are documented in `src/db.py`
  (`SCHEMA`) and `docs/data-logging.md`.

## Gotchas

- **Edits aren't live until restart** — same rule as the rest of the app. After
  changing `src/dashboard/` or the config, `sudo systemctl restart
  jukebox-dashboard`.
- **`data/dashboard/requests.parquet` is gitignored** (under `data/`, plus an
  explicit `*.parquet` rule). The dashboard *code* is committed; the data is not.
- **Stale view right after a request** is expected (up to the snapshot interval).
  The header shows snapshot age so you can tell a slow refresh from a real gap.
- **Dependencies** (`fastapi`, `uvicorn`) are installed `--user` via
  `requirements.txt`, same as `duckdb`, so the systemd `/usr/bin/python3` finds
  them under `~/.local`.
